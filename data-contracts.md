## 1. Идентификаторы и время

| Идентификатор | Область уникальности и смысл |
|---|---|
| `site` | Сайт в своей системе. Приёмник определяет его по ключу доступа. |
| `source` | Система **и аккаунт** источника: например, `crm_demo` или `finance_demo`. |
| `visitor_id` | Браузер в области cookie. Это не подтверждённый человек и не сквозной ID всех устройств. |
| `session_id` | Сессия внутри сайта; объединяет события, формы и записи. |
| `stream_id` | Отдельный поток страницы или вкладки внутри сессии; устраняет коллизии локальной нумерации. |
| `request_id` | Одно обращение. Передаётся в форме, серверном результате и отдельном поле CRM. |
| `msg_id` | Одно сообщение. Создаётся до отправки и сохраняется при повторах. |
| `batch_id` | Одна неизменяемая пачка записи; сохраняется при повторной доставке. |
| Внешний ID | ID объекта вместе с `source`; одинаковые номера разных аккаунтов не склеиваются. |

Внутренние ID создавайте устойчивым генератором, например UUID.
`request_id` не равен `msg_id`: одно обращение порождает несколько сообщений.
Новое самостоятельное обращение получает новый `request_id`; повтор доставки
прежней попытки сохраняет старый. Сервер валидирует ID и при необходимости
выдаёт его сам, возвращая фактическое значение в ответе формы.

Для собственной реализации зафиксируйте правила начала/окончания сессии,
совместного использования ID вкладками и работы без хранилища браузера.
При отказе cookie допускается `visitor_id = NULL`, при невозможности
сохранить сессию — новая локальная сессия с признаком ограниченного покрытия.
Пустой ID можно дополнить; два разных непустых ID нельзя молча заменить
один другим. Независимые домены не получают общую cookie автоматически.

**Время:** `client_ts` — действие в браузере, `sent_at` — первая отправка,
`received_at` — приём сервером, `modified_at` — изменение внешнего объекта.
Храните их раздельно как время с часовым поясом; для обмена используйте UTC.
В отчётах задавайте часовой пояс и полуоткрытый интервал `[from, to)`.
Порядок внутри потока уточняет `seq`; несколько вкладок не образуют
идеально упорядоченную единую шкалу. Сроки серверной доставки нельзя
измерять только по часам браузера.

## 2. Слои и сущности

### Три слоя хранения

| Слой | Содержимое | Обязательная трассировка |
|---|---|---|
| Сырьё | Разрешённый очищенный JSON, метаданные приёма, версии внешних объектов. | Источник, ключ сообщения/объекта, время, версия формата и состояние разбора. |
| Сущности | Типизированные события, обращения, лиды, звонки, сделки, оплаты и расходы. | Ссылка на сырьё и версия преобразования. |
| Производные данные | Свёртка записи, текст, отношения, граф и витрины. | Версия построения, входные объекты/файлы и отметка актуальности. |

Сырьё означает «то, что разрешено принять», а не полную копию всех полей.
До передачи удаляйте секреты, значения ввода и лишние контакты; применяйте
списки разрешённых параметров URL, свойств событий и полей форм.
Загрузчики очищают ответы внешних API до сохранения в сырьё.
Сохраняйте исходный **очищенный** URL рядом с нормализованным. Fragment,
query, заголовки, текст DOM и сообщения ошибок тоже могут содержать данные.

### Минимальная логическая модель

`?` обозначает необязательное поле. Стрелки и ключи связи не обещают 1:1.

| Сущность | Ключ | Поля и назначение |
|---|---|---|
| `session` | `(site, session_id)` | `visitor_id?`, начало/последнее действие, очищенный входной URL и метки источника. |
| `event` | `(site, event_id)` | `session_id`, `stream_id`, `seq`, `name`, `client_ts`, `raw_id`. |
| `request` | `(site, request_id)` | `session_id?`, `form_id`, ссылки на копию и серверные результаты. |
| `crm_lead` | `(source, lead_id)` | `site?`, `request_id?`, `modified_at`, `raw_id`. |
| `call` | `(source, call_id)` | Время, результат, мосты посетителя/CRM при наличии, `raw_id`. |
| `deal` | `(source, deal_id)` | Стадия, сумма, валюта, время изменения, ссылка на сырьё. |
| `payment` | `(source, payment_id)` | `deal_source?`, `deal_id?`, `paid_at`, `amount`, `currency`, `status`. |
| `cost` | `(source, report_key, day, channel_key, currency)` | Сумма выбранного отчёта; `report_key` фиксирует фильтры, измерения и часовой пояс. |
| `relation` | Устойчивый ключ типа и обоих концов | Ключи сущностей с их областями, основание, уверенность и версия правила. |

Лиды и сделки могут относиться к разным обращениям; храните такие переходы
в `relation`, а не одним полем, которое теряет остальные связи.
У оплаты из учётной системы `source` может отличаться от CRM: для связи
со сделкой нужны **оба** поля `deal_source` и `deal_id` либо отдельное
объяснимое отношение. Одного номера сделки недостаточно.

```text
(site, visitor_id) -> (site, session_id) -> (site, request_id)
                             |                     |
                      events + files         (source, lead_id)
                             |                     |
                      (source, call_id)      (source, deal_id)
                                                   |
                                            (source, payment_id)
```

У сущностей есть собственные строки даже без найденного соседа. Не теряйте
непривязанные оплаты и звонки из-за `INNER JOIN`. При допустимой задержке
загрузки сохраняйте внешний ключ источника как факт и проверяйте отсутствие
соседа отдельным аудитом; подтверждённое отношение строится после появления
обоих концов.

### Служебные данные

| Реестр | Минимально необходимые сведения |
|---|---|
| Сайты и ключи | Сайт, разрешённые Origin/виды сообщений, статус ключа; серверные секреты отдельно. |
| Входящие сообщения | Уникальность `(site, kind, msg_id)`, очищенное тело, `new/ok/failed`, версия/ошибка разбора. |
| Внешние версии | Источник, вид объекта, внешний ID, версия/хеш содержимого, время приёма. |
| Файлы записей | Сайт, сессия, ключ S3, размер, SHA-256, диапазоны потоков, полнота и срок хранения. |
| Запуски и курсоры | Источник/задача, область окна, начало/конец, статус, счётчики, последний полный курсор. |
| Производные результаты | Версия, перечень входов, время построения, признаки устаревания и неполноты. |

Неизвестная версия формата остаётся в сырье со статусом ошибки разбора;
синтаксически неверный JSON не считается принятым и отражается в отказе.

## 3. Приём событий и форм

### Маршруты и доступ

| Маршрут | Вход / выход | Граница доступа |
|---|---|---|
| `POST /v1/inbox` | Массив сообщений `event`, `form_copy`, `form_result`; результат по каждому элементу. | Браузерный ключ: первые два вида; серверный секрет: `form_result`. |
| `POST /v1/rec` | Одна пачка записи; `accepted` или `duplicate`. | Ключ сайта, допустимый Origin и включённый флаг записи. |
| `GET /v1/flags` | Разрешение записи и версия публичной конфигурации. | Ключ сайта и Origin; без секретов и внутренних правил. |
| `GET /health` | Доступность приёмника. | Без клиентских данных; подробная свежесть задач доступна служебной роли. |
| `POST /v1/call-hook` | Уведомление телефонии. | Отдельная проверка подлинности по контракту поставщика. |

Для учебной реализации используйте `Authorization: Bearer <ключ>`.
Ключ выбирает `site`; поле сайта в теле не позволяет изменить эту область.
Поддержите браузерный `OPTIONS`, точный список Origin и нужных заголовков.
Серверный запрос проверяется отдельным секретом и не требует Origin.

**Браузерный ключ публичен.** CORS и Origin не доказывают подлинность
посетителя вне браузера. Нужны ограничения частоты, объёма, распаковки
и наблюдение за мусорным трафиком. Браузерные сообщения сами по себе
не подтверждают принятие формы или платёж.

### Тело запроса с одним событием

```json
[
  {
    "v": 1,
    "kind": "event",
    "msg_id": "ev_demo_01",
    "session_id": "s1",
    "visitor_id": "v1",
    "stream_id": "tab1_page1",
    "seq": 1,
    "name": "page_view",
    "url": "https://www.example.com/prices",
    "ts": "2026-11-16T10:00:00Z",
    "sent_at": "2026-11-16T10:00:01Z"
  }
]
```

В этой модели `msg_id` события становится `event_id`, `ts` — `client_ts`.
`received_at` и `site` добавляет сервер. Версия и `kind` выбирают разбор.
Конверт после первой отправки неизменяем; повтор с тем же ключом и другим
содержимым — конфликт, а не обновление старого действия.

Для всех видов нужны `v`, `kind`, `msg_id`, `ts`, `sent_at`.
Дополнительные поля:

| Вид | Обязательные поля | Необязательные сведения |
|---|---|---|
| `event` | `session_id`, `stream_id`, `seq`, `name`, `url`. | `visitor_id`, разрешённые свойства. |
| `form_copy` | `request_id`, `form_id`, `url`. | `session_id`, `visitor_id`, разрешённые поля без контактов в учебном варианте. |
| `form_result` | `request_id`, `form_id`, `result`: `accepted` или `rejected`. | Машинная причина отказа без значений полей. |

Каждая копия и каждый серверный результат имеют собственный `msg_id`.
История этих фактов сохраняется; сводная строка `request` не заменяет её.
`accepted` означает решение обработчика сайта, а не создание лида CRM.

### Подтверждение и повтор

Пример ответа на пачку из трёх элементов: новый, повторный и неверный.
Индексы начинаются с нуля.

```json
{
  "accepted": [0],
  "duplicate": [1],
  "rejected": [{"i": 2, "error": "bad_envelope"}]
}
```

Каждый входной индекс появляется ровно в одном списке. Подтверждение
`accepted` выдаётся только после надёжного сохранения сырья.
При разборе сущность и статус `ok` меняются одной транзакцией.

```text
receive -> validate -> commit raw(new) -> acknowledge
                              |
                            parse -> commit entities + raw(ok)
                              |
                              +----> raw(failed, reason)
```

| Ответ | Действие отправителя |
|---|---|
| `200` | Прочитать поэлементный результат. Удалить из outbox только принятые и повторы; постоянные отказы отделить. |
| `400/401/403/415` | Исправить данные, доступ или формат; не повторять бесконечно. |
| `413` | Уменьшить пачку, сохранив ID элементов. Слишком большой одиночный элемент пометить отказом. |
| `429/503`, обрыв сети или потеря ответа | Повторить неподтверждённые сообщения с прежними ID, паузой и ограниченным возрастом очереди. |

Если все элементы отклонены, верните `400` с тем же форматом ошибок.
На повтор с изменённым телом верните поэлементный `id_conflict`;
для отдельной пачки записи — `409`. Ограничения очереди и число
отброшенных сообщений видимы в диагностике. Наличие ID сессии в
`localStorage` не заменяет outbox сообщений.

## 4. Контракт записи поведения

Пачка содержит `v`, `session_id`, `stream_id`, `batch_id`, диапазон
`seq_from/seq_to`, события rrweb и признаки усечения. Порядок и дедупликация
внутри потока опираются на `(stream_id, seq)`, не на порядок HTTP-запросов.
Приёмник проверяет совпадение диапазона с содержимым. Ключ повтора пачки —
`(site, session_id, batch_id)`, ключ события записи —
`(site, session_id, stream_id, seq)`. Трекер и рекордер ведут отдельные
последовательности: их номера не смешиваются между типами данных.

Для каждого потока нужны начальный полный снимок DOM и последующие
изменения. Дублирующие записи одинакового ключа должны совпадать;
конфликт отмечается, а не выбирается произвольно.

```text
batch -> durable local buffer -> immutable compressed file -> S3
                                        |                   |
                                        +---- register <----+
                                                |
                                  verify -> remove local copy

catalog + main + late files -> player / fold -> events + text
```

| Артефакт | Контракт готовности |
|---|---|
| Буфер | Подтверждённые пачки переживают перезапуск процесса и контейнера; повтор безопасен. |
| Архив | Версия формата, ID сессии/потоков, события, диапазоны, пропуски и контрольная сумма. |
| Каталог | Файл зарегистрирован после проверки загрузки; ключ и SHA-256 позволяют безопасно повторить шаг. |
| Плеер | Проверяет доступ, размер и распаковку; показывает пропуски, отсутствие снимка и усечение. |
| Свёртка | Время, поток, вид действия, очищенный URL и разрешённое имя элемента; ссылка на файл/позицию. |
| Текст сессии | Объяснимая последовательность производных событий, версия и перечень входных файлов. |

Файл и БД не образуют общую транзакцию. Проверьте сбой между записью
буфера и отметкой приёма, а также между S3 и регистрацией каталога.
Повтор должен завершить операцию без потери единственной копии.
Поздние данные создают отдельный неизменяемый файл и помечают прежнюю
свёртку устаревшей. События и текст нового поколения публикуются согласованно.

Маскируйте чувствительные узлы, атрибуты и ввод **до записи**. Свёртка
не восстанавливает введённые значения. Тип и длину ввода сохраняйте,
только если выбранный безопасный формат позволяет их получить.
Ошибки JavaScript требуют отдельного обработчика и очистки; сам факт
подключения rrweb не гарантирует их сбор.

Запись DOM — не видео. Ресурсы страницы могут измениться; для длительного
хранения нужно разрешённое архивирование ресурсов или явно ограниченная
гарантия воспроизведения. Плеер изолируйте от основного приложения:
скрипты записи и внешние ресурсы не должны получать его привилегии.

## 5. Внешние источники и связи

Для каждого адаптера создайте карту полей: внешний путь → учебное поле,
тип, необязательность и преобразование. Начальная загрузка охватывает
явный исторический период; последующие — изменения с пагинацией.
Если API не даёт надёжной метки изменения, адаптер использует повторные
окна/сверочные снимки и объявляет ограничение покрытия.

```text
last cursor -> bounded window -> all pages -> raw versions -> entities
                                                               |
                                                       commit cursor
failure before completion -> retain old complete cursor -> repeat
```

Курсор продвигается только за полностью сохранённое и обработанное окно.
Повтор окна не создаёт неизменённых версий. Нужны повторная загрузка
изменяемой истории и политика удалений: частичная выборка или отказ
в правах не доказывают, что все отсутствующие объекты удалены.

### Метаданные отношения

| Поле | Смысл |
|---|---|
| `type`, `from`, `to` | Тип связи и полные ключи обоих концов с сайтом/источником. |
| `basis` | Объяснение: явный `request_id`, внешний CRM-переход, мост поставщика или кандидатное совпадение. |
| `confidence` | `confirmed`, `candidate` или `ambiguous`; это категории, не вычисленная вероятность. |
| `rule_version` | Версия правила своей реализации. |
| `built_at`, `provenance` | Время и ссылки на исходные строки/версии. |

Несколько подходящих соседей не превращаются автоматически в один
подтверждённый. Телефон или близкое время сами по себе не гарантируют
идентичность посетителя. Подтверждённые пути и кандидатные гипотезы
разделяйте в витринах и ответах агента.

## 6. Денежные витрины

| Набор | Одна строка означает | Контроль |
|---|---|---|
| Сделки | Актуальное состояние одной сделки в одном источнике. | Сумма и стадия не подменяют оплату. |
| Платежи | Одно денежное движение с устойчивым ID и статусом. | Связь с CRM не меняет общую сумму; неизвестная сделка допустима. |
| Расходы | Одну строку выбранного отчёта за день, канал и валюту. | Не суммировать пересекающиеся отчёты по каналам и кампаниям. |
| Атрибуция | Распределение выбранной метрики по каналам. | Сумма распределённых и нераспределённых денег равна контрольному итогу. |

Для учебного набора `amount` — decimal, валюта обязательна;
в JSON суммы передаются строками. Учитываются только движения `settled`.
Оплата положительна, возврат — отдельное отрицательное движение;
отменённое движение не входит в итог. Реальные статусы и знаки
адаптер приводит к этому договору, сохраняя исходную версию.

Перед соединением задайте детализацию отчёта, временную ось и правило
канала. В простом пилоте у сделки один подтверждённый канал либо
`unassigned`; период оплат определяется `paid_at`. Для нескольких касаний
нужно отдельное распределение, сохраняющее общий итог.

```text
payments -> aggregate(day, attributed_channel, currency) --+
                                                         +-> report
costs    -> aggregate(day, channel, currency) -------------+
```

Сначала агрегируйте обе стороны до одинаковых измерений, затем соединяйте
с сохранением строк, присутствующих только с одной стороны.
Не соединяйте две оплаты с тремя строками расходов напрямую: получится
шесть строк и размноженные суммы. Валюты считайте отдельно; пересчёт
требует самостоятельного источника курса и правила даты.
Поступления и расходы за один день не доказывают окупаемость когорты.

## 7. Контракт чтения для агента

Предложите ограниченные инструменты: словарь данных, качество/свежесть,
SQL-чтение витрин, поиск графового пути, события и текст сессии.
Полные записи доступны отдельному разрешённому инструменту по необходимости.
Права чтения обеспечиваются БД и графом, а не только текстом инструкции.

Пример результата инструмента, вернувшего полный учебный итог:

```json
{
  "data": [{"currency": "XXX", "paid": "100.00"}],
  "as_of": "2026-11-17T01:00:00Z",
  "period": {"from": "2026-11-16T00:00:00Z", "to": "2026-11-17T00:00:00Z"},
  "timezone": "UTC",
  "row_count": 1,
  "truncated": false,
  "coverage": {"payments": "complete", "crm": "complete"},
  "warnings": [],
  "provenance": ["demo_fixture"]
}
```

`XXX` — учебное обозначение без реальной валюты. `as_of` определяется
покрытием источников, а не временем вызова инструмента. `row_count`
означает число возвращённых строк, а не общий размер выборки.
Несколько графовых путей могут вести к одному платежу: перед суммированием
оставляйте одно движение на `(source, payment_id)`.
Неполный набор помечается `truncated`; итог по усечённым строкам
агент не суммирует как полный. При ошибке возвращается явная ошибка,
а не пустой успешный набор.

Каждый ответ агента называет период, определение метрики, свежесть,
основания связей и ограничения. Содержимое CRM, DOM и файлов считается
данными и не разрешает команды, смену прав или обход ограничений.
