# Приёмка системы

[Обзор](README.md) · [Контракты](data-contracts.md) · [Сборка](build-and-operations.md)

**Назначение главы:** проверить результат на наблюдаемых данных.
Все сценарии выполняются на отдельном учебном стенде. Проверки реальных
API проводят дополнительно после подключения каждого источника.

**В этой главе:** [контрольный набор](#1-контрольный-набор) ·

## 1. Контрольный набор

Используйте дату `2026-11-16`, пояс UTC и учебную валюту `XXX`.
Период отчёта: `[2026-11-16T00:00:00Z, 2026-11-17T00:00:00Z)`.
Все перечисленные платежи и расходы входят в этот период.

| Объект | Входные данные |
|---|---|
| Сайт и браузер | Сайт `demo`, URL `https://www.example.com`, посетитель `v1`, сессия `s1`. |
| Обычные события | Два `page_view` для `/` и `/prices`, одно `form_submit`; три разных `msg_id`. |
| Запись | Два потока страниц с начальными снимками, переход, клик и прокрутка; всё в `s1`. |
| Обращение | `request_id=r1`, копия формы и серверный `accepted` с разными `msg_id`. |
| CRM | Источник `crm_demo`, лид `l1` с `site=demo`, `request_id=r1`; явный переход к сделке `d1`. |
| Атрибуция пилота | Сделка `crm_demo/d1` имеет один подтверждённый канал `demo_cpc`. |
| Оплаты | Источник `finance_demo`, платежи `p1=40.00`, `p2=60.00`, оба `settled`, `deal_source=crm_demo`, `deal_id=d1`. |
| Звонки | Источник `voice_demo`: `c1` с проверенным мостом к `demo/v1`, `c2` без моста. |
| Расходы | Источник `ads_demo`, один отчёт `daily_channels`: каналы `demo_cpc=2.00`, `demo_email=3.00`, `demo_other=5.00`. |

**Ожидания после полного разбора:**

| Проверка | Ожидаемый результат |
|---|---|
| События и сессии | 3 события, 1 сессия; события разных потоков не конфликтуют. |
| Формы и CRM | 1 обращение, 1 лид, 1 сделка; путь `r1 → l1 → d1` подтверждён. |
| Сырьё приёмника | 5 принятых сообщений: 3 события, 1 копия и 1 серверный итог; пачки rrweb учитываются отдельно. |
| Оплаты | 2 движения; общий итог `100.00 XXX`, и столько же по `crm_demo/d1`. |
| Расходы | 3 строки выбранного отчёта, общий итог `10.00 XXX`; у `demo_cpc` — `2.00 XXX`. |
| Звонки | 2 звонка; `c1` связан с посетителем, `c2` сохранён без выдуманной связи. |
| Поведение | Запись доступна, два потока различимы, действия и текст прослеживаются до файлов. |
| Граф и агент | Подтверждённый путь до двух оплат; контрольный ответ даёт 100, а не сумму сделки. |

Число файлов зависит от выбранного закрытия и не является фиксированным
ожиданием. Проверяются состав потоков, контрольные суммы, воспроизведение
и полнота. Запись может быть неполной; агент должен объявить это.

### Независимые расширения набора

Каждый сценарий ниже начинается с чистого базового набора, чтобы ожидания
не зависели от порядка тестов.

| Дополнительный вход | Ожидание |
|---|---|
| Возврат `-20.00`, статус `settled` | Чистые поступления `80.00 XXX`; видны исходные оплаты и возврат. |
| Отменённый платёж `20.00` | Контрольный итог остаётся `100.00 XXX`. |
| Платёж `30.00` без найденной сделки | Общий итог `130.00 XXX`; `100.00` связаны, `30.00` относятся к `unassigned`. |
| Оплата в другой валюте | Отдельная строка итога; суммы разных валют не складываются. |
| Второй CRM-аккаунт с `deal_id=d1` | Две разные сделки; оплаты не переходят между ними по одному номеру. |
| Обращение с серверным `rejected` | Отказ формы; лид не создаётся системой сверки. |

## 2. Сквозной прогон

1. Поднимите пустой стенд и примените миграции. Проверьте роли, ключи и Origin.
2. Пройдите контрольные страницы через настоящий браузерный скрипт.
   Проверьте сообщения, outbox и запись; одной вставки SQL для этой части мало.
3. Отправьте форму через тестовый обработчик. В имитации CRM сначала
   задержите лид, затем верните его с тем же `request_id`.
4. Загрузите сделки, оплаты, звонки и расходы через адаптеры имитаций API.
   Дождитесь завершения окон и обработки сырья.
5. Закройте запись, проверьте S3 и плеер, выполните свёртку и экспорт графа.
6. Сравните числа из таблицы и SQL ниже с ответами инструментов агента.
7. Повторите **те же сообщения с прежними ID** и окна API.
   События, денежные суммы и неизменённые версии не увеличиваются;
   записи запусков и попыток могут увеличиться.
8. Выполните независимые расширения и матрицу отказов. Сохраните протокол:
   вход, воздействие, ожидаемый и фактический результат, команду и код завершения.

Воспроизводимую автоматическую приёмку агент оформляет в `test-acceptance`.
Браузерный smoke-тест и тестовые API входят в её описанный сценарий;
ручные шаги должны быть явно названы. Синтетический прогон подтверждает
свою реализацию, а не доступность методов и полей реального поставщика.

## 3. Контрольные SQL-запросы

Запросы используют учебные имена таблиц из контрактов. Выполняйте их
после обработки очередей; до этого отсутствие сущности может быть задержкой.

### События без сессии

```sql
SELECT e.site, e.session_id, COUNT(*) AS orphan_events
FROM event AS e
LEFT JOIN session AS s
  ON s.site = e.site AND s.session_id = e.session_id
WHERE s.session_id IS NULL
GROUP BY e.site, e.session_id;
```

На базовом наборе результат пустой. В отдельном негативном тесте удалите
или не создайте соответствующую сессию и убедитесь, что аудит её находит.
Для реальных данных вывод требует диагностики, а не автоматического удаления.

### Оплаты по сделке с учётом обоих источников

```sql
SELECT source, deal_source, deal_id, currency, SUM(amount) AS paid
FROM payment
WHERE status = 'settled'
GROUP BY source, deal_source, deal_id, currency;
```

Базовый результат: `finance_demo / crm_demo / d1 / XXX / 100.00`.
В расширении без сделки запрос также сохраняет группу с пустыми ключами
CRM; её нельзя терять на последующем соединении.
Для отчёта за период добавьте фильтр по `paid_at` с границами из начала главы.

### Итог до присоединения графа и расходов

```sql
SELECT currency, SUM(amount) AS paid
FROM payment
WHERE status = 'settled'
  AND paid_at >= '2026-11-16T00:00:00Z'
  AND paid_at <  '2026-11-17T00:00:00Z'
GROUP BY currency;
```

Сравните эти суммы с итогом витрины по всем каналам, включая `unassigned`.
Они должны совпасть. Отдельно сверяйте расходы с выбранным отчётом источника;
их присоединение не изменяет число платежей и сумму поступлений.

## 4. Матрица отказов

Для каждой строки проверяются и видимый статус, и фактическое состояние
хранилища. Успешный HTTP-ответ сам по себе не является приёмкой.

| Воздействие | Что должно произойти |
|---|---|
| Потерян ответ после сохранения события | Повтор с тем же ID даёт `duplicate`; одно событие в сущностях. |
| Один ID с другим содержимым | Явный конфликт; прежний факт не перезаписан. |
| Смешанная пачка | У каждого индекса один исход; годные сохранены, постоянные отказы отделены. |
| Чужой Origin, отозванный ключ или серверный вид с браузерным ключом | Отказ; чужие данные не сохранены в нужной области. |
| Превышение тела, распаковки или частоты | Ограниченный отказ; приложение не расходует неограниченную память и не подтверждает несохранённое. |
| Недоступна аналитика при форме | Штатный обработчик и доставка CRM работают; очереди аналитики ограничены и наблюдаемы. |
| Обрыв разбора | Нет половины транзакции; повтор не создаёт дубликат сущности. |
| Сбой после записи буфера, до отметки БД | Повтор и закрытие не удваивают действия; единственная подтверждённая копия не теряется. |
| S3 не отвечает или регистрация каталога прервалась | Локальная копия остаётся; повтор завершает загрузку/регистрацию без молчаливой перезаписи конфликта. |
| Пропуск, поздняя пачка или нет полного снимка | Неполнота видима; поздние входы делают прежнюю свёртку устаревшей. |
| Сбой середины окна API | Последний полный курсор сохранён; повтор не теряет страницу и не создаёт новые неизменённые версии. |
| CRM устарела или после смены прав вернула пусто | Нет вывода о потере всех заявок или массовом удалении объектов. |
| Изменилась подтверждённая связь | Старое отношение перестало действовать в SQL и графе; поколения и свежесть видны. |
| Усечён ответ инструмента | `truncated=true`; агент не считает видимые строки полным итогом. |
| Команда спрятана в CRM/DOM или запрошена запись через read tool | Команда остаётся данными; хранилище запрещает изменение. |
| Секрет помещён в URL, DOM, атрибут и поле формы | Он отсутствует в переданном сырье, архивах, свёртках, тексте и журналах. |
| Потерян основной сервер | На другом стенде восстановлены БД и файлы; проверены запись, суммы и права. |
| Удалён тестовый набор по сроку | Он недоступен во всех рабочих слоях; после восстановления старой копии применяется политика повторного удаления. |

## 5. Когда принимать результат

### Три уровня готовности

| Уровень | Что подтверждено |
|---|---|
| **Учебная сборка** | Контрольный сценарий и отказы пройдены на имитациях; команды запуска повторяемы. |
| **Подключённый пилот** | Для каждого реального источника проверены поля, права, покрытие истории, статусы и сверка контрольных сумм. |
| **Эксплуатационная готовность** | Нагрузка укладывается в выбранные пределы; наблюдение, доступ, удаление и восстановление проверены на стенде. |

Не заменяйте один уровень другим: наличие исходного кода не означает
проверенную интеграцию, а работающий API не доказывает восстановление.

### Комплект сдачи от агента

- [ ] Спецификация пилота и зафиксированные версии зависимостей.
- [ ] Миграции, роли, карта источников и формальные схемы сообщений.
- [ ] Конфигурация без секретов, точные команды запуска и `runbook`.
- [ ] Синтетические фикстуры и повторяемый сквозной тест с фактическими результатами.
- [ ] Словарь метрик, детализация витрин и сверка денег до/после атрибуции.
- [ ] Основания отношений, свежесть проекций и примеры ответов агента.
- [ ] Протокол проверки маскирования, прав, восстановления и удаления.
- [ ] Перечень неподключённых источников, ограничений и оставшихся решений.

**Граница руководства:** оно задаёт технический каркас и критерии сборки.
Агенту предстоит написать приложение, миграции, адаптеры, инструменты и
тесты. Поля и возможности конкретных API проверяются во время реализации;
бизнес-определения и допустимые риски принимает владелец своей системы.
